## What this change does

F-016 Phase 4 — the lead becomes a pure dispatcher. The blocking
5–20+ minute `cycle_review` MCP tool becomes a fast dispatcher that
hands off to the F-016-U-5 watcher daemon when both `NTFY_TOPIC` is
set AND the daemon is running; otherwise it stays blocking and
surfaces a one-line setup nudge (env var or daemon-down, chosen by
why).

Three MCP tools ship in this PR:

- **`cycle_review_async`** — daemon-driven handoff. Returns ≤2s;
  validates the unit + checks daemon liveness via the `daemon_locks`
  heartbeat, then lets the daemon's next tick pick the unit up
  (`list_active_units` already returns every row this tool needs).
  No `_run_*_advance` call, no worker wait, no full F-014 probe.
- **`cycle_review_blocking`** — explicit pre-Phase-4 behaviour. Same
  body as today's `cycle_review`: shares
  `_run_tester_advance` / `_run_reviewer_advance` /
  `_run_terminal_advance` with the `advance_to_*` phase commands —
  no duplicate transition table.
- **`cycle_review`** — the dispatcher: `NTFY+daemon` → async;
  `NTFY unset` OR daemon down → blocking + nudge.

`scheduling._run_one` is updated to route through
`cycle_review_blocking` explicitly so `parallel_units` /
`parallel_units_global` keeps its "finish when the unit reaches
terminal" contract regardless of how the default-flip is configured.

Deviations from spec:

- The dispatcher adds a third branch (`NTFY_TOPIC` set + daemon down
  → blocking + warning) that the spec didn't explicitly enumerate. The
  spec's two-state framing (NTFY set vs. unset) assumed the daemon is
  always up when NTFY is set. The proposal's Risk R1 ("if the daemon
  dies, units freeze until it restarts") makes the fallback necessary;
  treating a dead daemon as "silently strand the unit" is the regression
  the safety net prevents. Test
  `TestCycleReviewDispatcher::test_ntfy_set_but_daemon_down_falls_back_to_blocking`
  pins the behaviour.

Predecessor alignment:

- Reuses F-016-U-5's `state.get_daemon_lock` /
  `DEFAULT_DAEMON_LOCK_STALE_AFTER_S` for the daemon-health probe —
  same 30s heartbeat threshold `claim_daemon_lock` uses for stale
  takeover, so the dispatcher never calls a daemon 'alive' that the
  takeover path would already reclaim. The U-5 cycle log (PR #61) made
  this CAS-based ownership the load-bearing primitive; this PR
  consumes it read-only.
- Honors U-5's `list_active_units` contract: the async handoff is a
  no-op enqueue because the daemon's per-tick walk already covers
  every active status the dispatcher will see.

## Decisions/deviations from the unit description

- The unit description says "`cycle_review_blocking` calls the
  daemon's engine in-process so there is no duplicate transition
  table." This PR satisfies the no-duplicate constraint by sharing
  the existing `_run_*_advance` helpers between the blocking variant,
  the dispatcher, and the `advance_to_*` phase commands. Physically
  relocating those helpers to a shared `orchestrator/cycle/phases.py`
  module is U-7's scope per the proposal ("Phase 5 — Cleanup"); doing
  it in this PR would expand the diff into the next unit.
- The async handoff path does not synchronously trigger a daemon tick
  — the daemon's poll loop reads `list_active_units` each tick, so
  the unit is observed within `poll_interval_s` (default 5s) of the
  call. Forcing an immediate reconcile would add network round-trips
  per the worker tail and break the "≤2s" acceptance.
