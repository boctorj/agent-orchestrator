## Unit
F-016-U-2 — Phase 1 of the dispatcher/watcher split (`docs/PROPOSAL-async-orchestrator.md`).

## What this change does

Wires the existing `spawn_async` / `wait_idle` into MCP and adds the matching `resume_async`. `spawn_unit_async` returns in ≤2s and persists `coder_session_id` immediately on receipt — killing the ghost-row failure class (`status=coding` with empty session_id, as F-014-U-1 documented).

Surface delta:

- **Worker protocol** (`orchestrator/workers/base.py`) gains `spawn_async` / `resume_async` / `wait_idle` with docstrings that describe the submit/wait split.
- **`ManagedAgentWorker.resume_async`** (`workers/managed_agent.py`) — 6 lines that submit a `user.message` event and return without opening a stream. Mirrors `spawn_async`'s send half.
- **`DockerClaudeCodeWorker`** — raises `NotImplementedError` for all three async primitives with a clear pointer to the proposal. Avoids silently blocking when a docker-configured lead calls the new MCP tools; an actual async split for docker is a follow-up unit per the proposal.
- **`spawn_unit_async` MCP tool** (`tools/execution.py`) — seeds the unit row (`status=coding` + branch) BEFORE the worker call, then persists `coder_session_id` on return. Mirrors `spawn_unit`'s validation + event surface. Returns `{unit_id, feature_id, session_id, branch, status, submitted_at}`.
- **`wait_unit` MCP tool** — `wait_idle` + the existing `_record_terminal_marker` recorder. Terminal marker → state advances + marker JSON. `TimeoutError` → `{status: "still_running", reason: "timeout"}`. Idle-with-no-marker → `{status: "still_running", reason: "no_marker"}` (Phase 1 wait is read-side; `cycle_review` keeps the no-marker → escalate policy).

## Manual verification

None beyond the test suite. The new MCP tools work on the `managed_agents` backend; `docker` callers get an actionable `NotImplementedError`.

## Spec satisfaction

Satisfies these acceptance criteria from `features/F-016/spec.md` (Phase 1, per `docs/PROPOSAL-async-orchestrator.md`):

- [x] `spawn_unit_async` p95 latency < 3 seconds on Managed Agents backend (no `wait_idle` in the path; tests assert direct `spawn_async` invocation, no blocking spawn fallback).
- [x] After `spawn_unit_async` returns, `get_unit_status` shows `status='coding'` and a non-empty `coder_session_id` (covered by `test_returns_session_id_and_coding_status`).
- [x] F-014-U-1-style ghost rows (status=coding, session_id="") are structurally impossible — the row is seeded before `worker.spawn_async` runs and the session_id is persisted before `spawn_unit_async` returns (covered by `test_session_id_persisted_before_spawn_async_returns` via an in-spawn observer).
- [x] Killing the lead between `spawn_unit_async` and `wait_unit` leaves the unit in `coding` with a live session_id; a fresh lead session can call `wait_unit` to resume (the persisted row + non-empty session_id is the necessary invariant; the resume path itself reuses the existing `ManagedAgentWorker.wait_idle` machinery).

Deviations from spec:
- None. The proposal's example output schema (`{unit_id, session_id, status, submitted_at}`) is preserved; `feature_id` and `branch` are added as useful extras the existing `spawn_unit` already surfaces.

Predecessor alignment:
- Builds directly on F-016-U-1 (PR #56): `_record_terminal_marker`'s `INSERT OR IGNORE` dedupe means `wait_unit` is safe to call repeatedly on the same idled session, and `scan_response` is the pure parser `wait_unit` relies on indirectly via `_record_terminal_marker`. The U-1 cycle log's `_KNOWN_ROLES` gate ensures `wait_unit("tooling", ...)` rejects at the role check rather than producing a spurious `tooling_blocked` event.

## Decisions / deviations

- **Docker backend punts to `NotImplementedError`.** The proposal explicitly flags this: "The Docker backend may need a parallel `spawn_async` / `wait_idle` / `resume_async` trio if it doesn't already split them — verify before scoping." The backend runs `docker run` synchronously, so an honest implementation would block for minutes — worse UX than a clear error pointing to the proposal. A follow-up unit owns the actual async split.
- **`wait_unit` no-marker path doesn't escalate.** The proposal's Phase 1 `wait_unit` is described as returning `{marker?, status, reason?}` on idle. Phase-1 wait is the read surface; `cycle_review` and the F-016-U-5 daemon own the no-marker → escalate policy. This keeps the new tool side-effect-light (it only writes the marker event when a marker matched).
- **`Worker` protocol declares the three async methods.** Per proposal step 2: "Add the matching `Worker` protocol methods in `workers/base.py`." Docker satisfies the contract by raising — that's the contract's intent (callers see backend-incompatibility immediately).
