## What this change does

Decomposes `cycle_review` into three idempotent phase commands and turns
`cycle_review` itself into a thin wrapper that calls them in sequence
through a shared internal engine.

New MCP tools (each `@mcp.tool()`-registered in `orchestrator/tools/execution.py`):

- **`advance_to_tester(feature_id, unit_id)`** — GATE 1 (CI on coder push) + tester
  phase + GATE 2 (CI on tester push). `already_past` when status is in
  `{reviewing, fixing, approved_awaiting_merge, done}`.
- **`advance_to_reviewer(feature_id, unit_id)`** — Copilot (best-effort) + reviewer
  fix-loop. `already_past` when status is in `{approved_awaiting_merge, done}`.
- **`advance_to_terminal(feature_id, unit_id)`** — optional F-007 ultrareview gate
  (when `feature.ultrareview_enabled` and the latest reviewer event is
  `reviewer_recommend_merge`) + terminal emit. `already_past` only when
  `status == done`.

All three return JSON `{unit_id, outcome, status, next_action, ...}` where
`outcome ∈ {advanced, already_past, escalated, not_ready}`.

`cycle_review` is now structurally identical to before but expressed as
three calls into shared `_run_tester_advance` / `_run_reviewer_advance` /
`_run_terminal_advance` helpers — both the new MCP tools and the wrapper
walk the same engine, satisfying the spec's "no parallel state machine"
constraint.

### Design notes (inline at the status-set definitions)

- **Why `approved_awaiting_merge` is NOT in `_PAST_TERMINAL_STATUSES`:**
  the `REVIEW_RECOMMEND_MERGE` marker flips status to that bucket
  BEFORE `advance_to_terminal` runs. Treating it as already-past would
  skip the ntfy push + cycle-log finalize. The narrow bucket is the
  spec's accepted asymmetry (PROPOSAL § Phase 2).
- **Why the wrapper shares one `CycleContext`** rather than nesting the
  three new MCP tools: one `_emit_terminal` call ⇒ one ntfy push, one
  cycle-log finalize, contiguous history. The proposal says "composed
  of public primitives"; the implementation makes the *engine* the
  contract (per spec § "no parallel state machine"), and the MCP tools
  are thin wrappers around it.
- **`_last_reviewer_outcome(unit_id)`** reads events to decide ultrareview
  gating, so `advance_to_terminal` is self-contained (lead + daemon
  callers don't need to thread state between MCP calls).
