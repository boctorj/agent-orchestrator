## What this change does

Ships the three primitives the lead chat uses to influence a unit
while the (Phase 3) daemon drives it — without racing on state writes
or worker sessions — plus the stale-marker delta-review rule the
daemon will compose into its reconcile loop.

- `send_to_unit_async(unit_id, message, role="")` — submit-only mirror
  of `send_to_unit`; returns in ~1s after the user-message event lands
  on the worker's queue. Holds a per-unit advance-lock during the
  submit window so a Phase-3 daemon doesn't race
  `advance_state_machine` against an in-flight send. Default role is
  derived from current unit status per the spec's routing table when
  `role=""`; structured `{delivered, reason, role_diagnostics,
  next_steps}` errors on the not-actionable cases (terminal status,
  cancelled unit, missing session, resume_async error).
- `cancel_unit(unit_id)` — sticky cancel: archives every role's
  worker session (best-effort — a backend exception does NOT block
  the cancel), flips status to `cancelled`, stamps `cancelled_at`.
  Idempotent: a second call returns `already_cancelled` without
  re-archiving sessions. Downstream dep-evaluation treats cancelled
  as not-done.
- `update_unit_deps(feature_id, unit_id, depends_on)` — re-shape the
  DAG for future scheduling without touching any in-flight worker.
  Cycle detection + self-dep + unknown-unit rejection, validated
  in-memory before persisting so a would-be cycle never partially
  corrupts the plan.

Schema additions (per spec):
- `work_units.cancelled_at TEXT` — sticky terminal flag.
- `work_units.owner TEXT` — short-lived `'lead'` claim slot during the
  lock window. The Phase 3 daemon will reuse this column as the CAS
  target for terminal advances (`claim_unit_owner` /
  `release_unit_owner` ship now so the daemon adopts without a schema
  bump).

The stale-marker delta-review rule lands in
`orchestrator/stale_marker.py`: the pure classifier
(`classify_marker_freshness`, case A/B/C per spec) plus a state-aware
detector (`detect_stale_reviewer_marker`) that uses event-timestamp
ordering when SHAs aren't recorded. The audit-event helper
(`record_stale_marker_pending_delta`) is dedupe-keyed so a Phase-3
daemon ticking the same staleness writes one row.

`scheduling.next_ready_units` / `next_ready_units_all` gain a
`cancelled` bucket so the lead can surface cancelled-unit state
without it landing in `in_flight`.

CLAUDE.md updated with the three-primitive summary per spec
acceptance: "Observe any time. Send-message is ~1s. Cancel is sticky.
Graph edits are orthogonal."

Deviations from spec:

- `send_to_unit_async` is a NEW MCP tool rather than an in-place
  rewrite of `send_to_unit`. The spec's pseudocode uses the name
  `send_to_unit` for the async form, but per the "Additive at every
  step" constraint (spec § Constraints), changing `send_to_unit`'s
  return shape would regress existing chat callers that rely on the
  synchronous response. The legacy `send_to_unit` stays as the
  blocking escape hatch; Phase 4 (F-016-U-6) is where the default
  flips per the spec's `NTFY_TOPIC`-gated rollout.

- Stale-marker SHA capture deferred to F-016-U-5 (daemon). The pure
  classifier accepts SHAs as arguments and the state-aware detector
  falls back to event-timestamp ordering (which is strictly correct
  for "the coder pushed after the reviewer reviewed"). Persisting the
  exact head_sha at marker-emit time would require either modifying
  `_record_terminal_marker`'s signature (cross-cuts every caller) or
  adding a parallel SHA-capture event at each call site (multi-site
  churn). The daemon (Phase 3) will introduce a single capture
  helper as part of its reconcile-loop refactor; for Phase 2.5,
  the timestamp-based fallback is sufficient and the SHA path is
  ready to plug in.
