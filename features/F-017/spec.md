# F-017: Tighten cycle log format — TL;DR section restores conceptual content to predecessor injection

## Intent

Cycle logs (`features/F-XXX/U-N.md`) are auto-generated by the
orchestrator at terminal state per F-006. They serve three consumers:

1. **Downstream worker prompts** — injected as `## PREDECESSOR UNITS`
   context blocks via [`compose_*_task`](../../orchestrator/tools/__init__.py)
   in `orchestrator/tools/__init__.py`. The actual fetch happens at
   [`execution.py:57`](../../orchestrator/tools/execution.py#L57):
   `cycle_log.cycle_log_summary(dep_id)` for each declared dep.
2. The **lead** via `feature_memory(F-X)` — reads the full file.
3. **Human audit** — reads the file on disk or via `gh pr view`.

**Today's `cycle_log_summary` already trims the file before injection.**
It strips the verbatim `## Coder's PR description` block (anchored on
the next known operational section heading per
[`cycle_log.py:304-352`](../../orchestrator/cycle_log.py#L304))
and returns:

    # header
    ## PR (metadata)
    ## Cycle history
    ## Review threads

This keeps the prompt small but **drops the conceptual content** —
"what shipped," "downstream contract," "decisions worth knowing" — all
of which live in the verbatim PR body that just got stripped. What
remains is operational metadata (PR opened / TESTS_PASS /
REVIEW_COMMENT, plus truncated review-thread snippets), which is low
signal for a downstream worker trying to reason about the predecessor's
contract.

**This feature restores conceptual content to predecessor injection
without growing the prompt much:**

1. Add a `## TL;DR` section to new cycle logs, placed **between `## PR`
   and `## Coder's PR description`**. Section has three required
   sub-headings — `### What shipped`, `### Downstream contract`,
   `### Decisions worth knowing` — each capped to a handful of lines.
2. **No function rename, no caller change.** Because `## TL;DR` sits
   *above* the strip boundary (`## Coder's PR description`), the
   existing `cycle_log_summary` naturally includes it. Predecessor
   injection automatically gets the new content with zero changes to
   `execution.py` or `_render_context_blocks`.
3. The coder is responsible for filling the three sub-sections in
   their PR body; the writer mirrors them into the cycle log on
   terminal state.

Net effect: predecessor block grows by ~20-30 lines (the TL;DR
content) but trades operational noise for conceptual signal. Token
total per 3-predecessor task: ~150 lines today → ~210 lines after.
Modest growth; large quality gain.

Existing cycle logs are NOT back-filled — they remain immutable per
F-006. Workers reading old-format predecessors get whatever
`cycle_log_summary` returns today (operational metadata, no TL;DR).
No fallback path needed; legacy logs just lack the new section.

Defers to F-016 Phase 3: the orchestrator-as-sole-writer + auto-commit
policy. This feature is about content shape, not who writes.

## Acceptance

When the feature ships:

1. New cycle logs contain a `## TL;DR` section positioned between the
   `## PR` block and the `## Coder's PR description` block. Required
   sub-headings (`### What shipped` / `### Downstream contract` /
   `### Decisions worth knowing`) are always present — even empty,
   with a `_TBD_` placeholder under each — so the format is
   grep-stable.
2. `cycle_log_summary(unit_id)` semantics are **preserved**: still
   strips the verbatim `## Coder's PR description` block, still
   anchored on the same set of operational section headings. Because
   the new `## TL;DR` section sits above the strip range, it appears
   verbatim in the returned summary (wrapping `## TL;DR` heading
   retained; `###` sub-headings retained verbatim — nothing is
   "heading-stripped").
3. `read_cycle_log(unit_id)` is unchanged. The full file (including
   the TL;DR section) is what `feature_memory` and human audit read.
4. The auto-fill writer reads the coder's PR body for sub-sections
   named identically (`### What shipped`, etc.) and mirrors them into
   the cycle log. If the coder PR body omits any sub-section, the
   writer emits the sub-heading with a `_TBD — coder did not fill in
   this sub-section._` placeholder.
5. [`orchestrator/prompts/coder.md`](../../orchestrator/prompts/coder.md)
   instructs the coder to include the three sub-sections in their PR
   body (additive to the existing "Spec satisfaction" / "Decisions /
   deviations" template).
6. Existing cycle logs on disk are NOT modified (F-006 immutability
   invariant preserved).
7. Tests pin: format ordering (`## PR` → `## TL;DR` → `## Coder's
   PR description`), sub-heading presence + spelling, `cycle_log_summary`
   output contains the new section verbatim, predecessor injection
   contains TL;DR content end-to-end.

## Out of scope

- Back-filling existing cycle logs with TL;DR sections — they remain
  immutable per F-006.
- Renaming `cycle_log_summary` or introducing a parallel extractor.
  The existing function does the right thing once the writer adds the
  TL;DR section.
- Changing `_render_context_blocks` or
  [`execution.py:57`](../../orchestrator/tools/execution.py#L57) —
  the injection path already calls `cycle_log_summary`.
- Pruning the cycle history / review-threads sections from the full
  file. They remain part of `cycle_log_summary`'s output (and the
  full audit file).
- Changing what `feature_memory(F-X)` returns to the lead — still the
  full file.
- Auto-commit / daemon-ownership of cycle log writes — that's F-016
  Phase 3.

## Approach

**Writer (the only file that changes — content side):**

- Update [`cycle_log_render.py`](../../orchestrator/cycle_log_render.py)
  (which `cycle_log.py` calls) to emit the `## TL;DR` section between
  the existing `## PR` block and `## Coder's PR description` block.
- Source the three sub-sections by reading the coder PR body for
  sub-headings of the same name (`### What shipped`, etc.). Implement
  this as a small markdown sub-section extractor; absence yields the
  `_TBD_` placeholder.
- Update [`cycle_log.py`](../../orchestrator/cycle_log.py)'s
  `_CYCLE_LOG_SECTION_AFTER_PR_RE` allow-list **only if needed** —
  it's currently anchored on `## (Cycle history|Review threads|Spec
  deviations|Links)`. Since `## TL;DR` sits *before* `## Coder's PR
  description`, the regex doesn't need to know about it; the strip
  range starts after the TL;DR. Verify by test.

**Coder prompt (the only file that changes — instruction side):**

- Update [`orchestrator/prompts/coder.md`](../../orchestrator/prompts/coder.md)'s
  PR-description template to require the three sub-sections. Place
  them near the top of the PR body so the orchestrator can find them
  reliably and human reviewers see them first.

**No other code changes.** `cycle_log_summary` semantics are preserved
because of where the new section sits; `execution.py:57` already
calls `cycle_log_summary`; `_render_context_blocks` already injects
the result. The change is purely in writer output + prompt
instructions.

## Constraints

- **F-006 immutability preserved.** Existing cycle logs are read-only.
- **Backward compatible.** Logs without TL;DR continue to work —
  `cycle_log_summary` returns whatever's between header and PR body
  (today: nothing; new logs: TL;DR). Workers reading old-format
  predecessors get the same content they get today.
- **Deterministic.** The writer's sub-section extractor and the
  cycle-log render are deterministic on the same input.
- **No new dependencies.** Plain Python + the existing regex-based
  cycle-log helpers.

## Decisions

- **No new extractor function.** Copilot's PR #60 review (2026-06-05)
  pointed out that `cycle_log_summary` already exists at
  [`cycle_log.py:320`](../../orchestrator/cycle_log.py#L320) and is
  already called for predecessor injection. The cleanest implementation
  exploits the existing strip semantics rather than adding a parallel
  function: place `## TL;DR` *above* the strip boundary so it's
  naturally included. **Why:** avoids a function-naming collision,
  avoids a caller-migration step, and reuses well-tested code paths.
- **Insertion point: between `## PR` and `## Coder's PR description`.**
  Not "front matter" (cycle logs don't have YAML front matter; the
  file starts with a markdown H1). **Why:** the only structural slot
  that (a) sits above the strip boundary so `cycle_log_summary`
  preserves it and (b) sits below the PR identity so humans / Claude
  reading top-down see metadata before commentary.
- **TL;DR heading + sub-headings retained verbatim in the summary
  output.** Nothing about the TL;DR is "heading-stripped." The
  summary returned by `cycle_log_summary` contains
  `## TL;DR\n### What shipped\n...` exactly as written by the
  renderer. **Why:** the headings ARE the structure; stripping them
  would lose the grep-stability that the format relies on.
- **Empty sub-sections still emit the heading with a `_TBD_`
  placeholder.** Worker prompt content must be predictable. **Why:**
  callers and tests can rely on heading presence; a missing sub-heading
  would signal a writer bug, not "no content."

## Open questions

- Should the auto-fill writer accept the sub-sections under
  alternative names (e.g., `### What changed`, `### What this ships`)
  or strictly require the canonical `### What shipped`? Leaning
  strict for now — it forces coder-prompt discipline. Revisit if
  reviewers report frequent mismatches.
- Should `feature_memory(F-X)` switch to also include the TL;DR
  prominently (e.g., as a "Per-unit highlights" block at the top)?
  Currently out of scope; the lead reads the full file and finds the
  TL;DR there. A future F-018 could surface it.
