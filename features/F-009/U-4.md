## Unit ID

## What this change does
Promotes `approved_awaiting_merge` from a cycle_review return-string to a first-class `UnitStatus` literal that the dashboard, `list_in_flight`, `next_ready_units`, and `reconcile_unit_pr` all read from the same row. Closes audit Gap H — the dashboard's 'Awaiting your merge' bucket previously queried for a status nothing wrote, so it was permanently empty.

Two write sites land the new status:

1. **`cycle_review._emit_terminal`** — when `outcome=='approved_awaiting_merge'`, flips the unit's row to `approved_awaiting_merge` (gated on an active from-state so a re-entry can't drift `done` back).
2. **`_record_terminal_marker` (from `send_to_unit`)** — `REVIEW_RECOMMEND_MERGE` now targets `approved_awaiting_merge` (not `in_ci`), so a reviewer endorsement via `send_to_unit` lands in the same bucket cycle_review's terminal would set.

Downstream-blocking semantics: a dep in `approved_awaiting_merge` does NOT unblock `ready_to_spawn` (only `status='done'` counts). The unit surfaces in a new `awaiting_merge` bucket in `next_ready_units` / `next_ready_units_all` — distinct from `in_flight` (no agent running) and from `escalated` (cycle finished cleanly). `list_in_flight` also surfaces it (the lead needs to remind the user what's pending).

`reconcile_unit_pr` learns the `approved_awaiting_merge + merged → done` branch (emits a `merged` event); still no-ops while the PR is open.

## Decisions/deviations from the unit description
- **Deviation:** the spec was ambiguous on where the `approved_awaiting_merge` unit surfaces in `next_ready_units` ("treats it as not in flight, not blocked, but not 'done'"). Added an explicit fourth bucket `awaiting_merge` rather than overloading `in_flight`, mirrored in `next_ready_units_all` aggregation. This is a JSON-shape addition (new key, plus `total_awaiting_merge` counter) but doesn't break any existing key consumers.
- **Refactor:** `_MarkerSpec.flips_in_ci: bool` widened to `target_status: str | None` so the spec table can express any post-marker target (not just in_ci or no-op). Closest precedent: keeping a 5-tuple of fields per marker rather than introducing a parallel boolean.
- The legacy `_is_awaiting_merge` event-driven helper in `dashboard.py` is preserved (still tested directly; could be removed in a follow-up). The bucket query no longer uses it — status is now authoritative.
- Out-of-scope finding: a stale in-memory `unit_state.status` is rewritten back over a fresh `touch_unit` flip in `spawn_reviewer` / `spawn_tester` between the worker.spawn and `_record_terminal_marker` calls (a pre-existing latent issue surfaced by reading this code carefully). Tests pass because the marker helper re-flips at the end, but it's worth a separate cleanup unit.
